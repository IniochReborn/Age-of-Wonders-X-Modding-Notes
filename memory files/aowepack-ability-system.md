AoWEPACK.dll (base 0x55700000, file = VA-0x55700C00) ability architecture:

- TAbilityOwner: ability BITS via [vmt+0x4C] GetAbSet(id) (TCustomAbilityList.GetAbSet 0x5574E0E0, pure bit test) + ability-DATA record chain at [owner+0x10] (levels live here). GetAbilityData 0x5574F1C4 (eax=owner, edx=id → rec|nil; hooked by abdataguard cave @0x55811000). AssignAb 0x5574F1E4 deep-copies bits AND records. TAbstractUnit and TItem are both TAbilityOwner descendants.
- Level bytes: TMultiLevelAbilityData/TTurnUndead [rec+0xC]; TDispelMagic/THealing [rec+0xD]; TLeadership max([rec+0xC] own, [rec+0x10] aura).
- Hero query chain: THero.GetAbilityLevel 0x5578831C / GetAbilityName 0x557882DC → owner-finder 0x557881DC (best of: hero, carried THeroItems [hero+0x70], THeroInventory [hero+0x74]; compares [vmt+0x84] per owner) → ability [vmt+0x70] GetLevel(owner) / [vmt+0x58] GetName. Combat: TCombatUnit.GetAbilityLevel 0x55725028 → strat unit [vmt+0x144]. GetAttackRA reads level via [unit vmt+0x84] with id 0x20=Marksmanship (DM id 0x3C, Healing 0x2F).
- Items: TItem VMT 0x5570FAFC; active flag [item+0x1C]&1 (Activate 0x55794308); UpdateFromLibrary 0x55794438 assigns from library item (incl. AssignAb). Editor (AoWDevX) authors item abilities as BITS ONLY (imports AssignAb, never ExpandAbility) → item instances have bit but no level record.
- VANILLA BUG + FIX (build_item_ability_levels.py v3, applied 2026-08-20): items carry real level records (editor authors e.g. Marksmanship III) and the hero-window owner-finder resolves them, but ⚠ **the hero's OWN ability bit-set NEVER contains item-granted bits** ([THero vmt+0x4C] = own TCustomAbilityList.GetAbSet only; the merged set is the separate THero.GetAbilitySet 0x557882AC used by the exe UI). Combat paths query the strategic hero directly (GetAttackRA/GetDamageRA gate on [owner vmt+0x88] GetAbEnabled → own-bit test; tactical panel AoWTCPCK TTacticalCombatUnitHS.ListAbilities 0x42355C calls ability.GetName(owner=[[tcu+0x1C]+0x4C] strategic unit)) → item abilities invisible there. Fix: (a) GetLevel of TMultiLevelAbility 0x557651D8 / TTurnUndead 0x5576AE8C / TLeadership 0x557661C4: no own record → cave_findrec @0x558124A0 searches THero/TLeader item containers FIRST ([hero+0x70] THeroItems, [hero+0x74] THeroInventory, TList at [container+8], record chain [item+0x10]) → item record's level; else own-bit → 1 : 0; (b) both RA marksmanship gates (`mov ecx,[eax]; call [ecx+0x88]` @0x5576E66E / 0x5576E626) → cave_msgate @0x55812520: virtual GetAbEnabled, else hero/leader with item record counts as enabled. Verified at runtime via diag wrapper + itemablvl_probe.py (owner in tactical combat = live TLeader, DLL at preferred base). Monster Slaying is an MLA (mod flyweight) → covered; its melee bonus reads via combat [vmt+0xB0] → strat [vmt+0x144] → THero owner-finder 0x5578831C (item-aware natively). THero VMT 0x55711FEC, TLeader 0x55712238.
- Strategic-unit virtual slot +0x148 = GetAbilityEnabled (TAbstractUnit 0x5577F5E0 base; THero 0x5578827C = MERGED unit|items|inventory — the item-aware enabled query; use it from exe caves via virtual dispatch to stay rebase-proof). TUnitWindow.UseAbility @0x409E90 (AoWx.exe) gated on ability.GetEnabled(unit) at 0x409EF7 — patched (build_unitwin_item_use.py, cave @0x46E3D8) to fall back to [unit vmt+0x148]; fixes overland use of Spell Casting items by heroes without the base ability. AoWx.exe .idata slack now ~full (0x46E3F3..0x46E400 left).
- HEALING once-per-day machinery (mapped 2026-08-21): used-flag = [THealingAbilityData+0xC] (1=fresh, 0=used; stream tag 0xA), level [rec+0xD] (tag 0xB). THealingAbility true VMT 0x557217BC (⚠ nameptr-loc+32, NOT +44!): +0x58 GetName 0x5576BF90 (suffix "(used)" iff GetEnabled=0), +0x74 GetEnabled, +0xAC NewDay 0x5576BF58 (→SetUsed(owner,1) if IsClass TAbstractUnit && owner player == cl). SetUsed 0x5576BEEC(eax=abil,edx=owner,cl=flag) LAZILY CREATES the owner's record (so bit-less recs on heroes are a vanilla-possible state; owner record chain serializes bit-independently). Consume: THealingCA.Execute 0x5576BCE0 (no vanilla gate!) and THealingTE.Execute 0x5576C6F8 (gates on GetEnabled @0x5576C775) both SetUsed(healer STRAT, 0) then HealUnit. Daily reset funnel: TAbilityOwner.NewDay 0x5574FE14 loops ids, dispatches [abil vmt+0xAC] only for own-bit abilities (funnel bit-test @0x5574FE33 hooked). Merged queries: THero/TLeader [vmt+0x148]=GetAbilityEnabled 0x5578827C (own leg 0x5577F5E0 → [vmt+0x14C] HasAbility + ability.GetEnabled; item legs 0x55786674/0x55786154 → item.GetAbEnabled 0x5574FD68 → ability.GetEnabled(item)), [vmt+0x14C]=merged HasAbility 0x557882AC. Containers store hero at [container+4]; TItem has NO carrier backref.
- ITEM-HEALING DAILY FIX (build_item_healing_daily.py, applied 2026-08-21): hero record = single source of truth. Caves 0x55812700–0x55812980: cave_ghe (VMT+0x74 repoint: no own bit → THero/TLeader merged [vmt+0x14C] bit, then own-rec used-flag), cave_mge (THero+TLeader VMT+0x148 repoint: 3 legs + healing tail-check on hero rec), cave_ndbit (@0x5574FE33: merged bit for id 0x2F), cave_cagate (@0x5576BD1A: CA.Execute validates GetEnabled(healer strat via helper 0x55810F00) before consume+heal, je 0x5576BD41 skips), cave_gan (@0x557882F0 in THero.GetAbilityName: healing used → display owner forced to hero), cave_expand2 (VMT+0xD0 repoint: fixes latent bug where Expand on a SetUsed-created level-0 rec set level 2 without SETBIT; now grants bit+level 1, preserves used-flag). Old cave_expand 0x5580E7F0 orphaned.
- ITEM-HEALING LEVEL FIX (build_item_healing_level.py, applied 2026-08-21): cave_healamt2 @0x558129A0 (amount level = max(own rec, item rec via cave_findrec) → 5/7/10; old cave_healamt 0x5580E6E0 entry = jmp to it, so cave_heal/est1/est2 all inherit) + cave_gname @0x55812A00 replaces THealingAbility.GetName wholesale (VMT+0x58 repoint @file 0x20C14, old 0x5576BF90 now dead incl. its gnplain hook): display level = max(GetLevel(owner), owner item rec) clamp 3, name via cave_lsnames, used-suffix keeps level ("Healing III (used)") using vanilla pieces (literals " ("@0x5576C03C, ")"@0x5576C048, resstring rec 0x557069F4 id 65450 "used" → LoadResString 0x55701210 → TranslateRStr 0x557249FC → 0x5570156C, _LStrCatN 0x55701198 pops its args, _LStrAsg 0x55701150, _LStrArrayClr 0x55701148). Delphi string temp pattern: zeroed stack slots + ArrayClr at end, no exception frame.
- ⚠ MULTIPLE UNIT COPIES AT RUNTIME (proven via heal_probe.py/ref_probe.py 2026-08-21): each hero exists as several live objects — server/world unit (TPlayer refs it), client/UI unit (exe-side object holds it), transient window copies, TFastCombatUnit strat twins ([fcu+0x4C]) from auto-combat sims. Action consumes hit ONE copy; state reaches display copies via the BIT-GATED ability merge 0x5574F518 (eax=dest, edx=source; per-id: source own-bit gate @0x5574F533 → level-compare → clone rec 0x557030CC(edx=[0x558FA048]) + RemoveAbilityData 0x5574F2B8(eax=owner,edx=id) + AddAbilityData + SetBit [vmt+0x50]). AssignAb 0x5574F1E4 (full replace) copies the record chain UNCONDITIONALLY; TAbilityOwner.ReadWrite streams recs via an id-LIST (tag 0x31) built from the chain — also bit-independent. So bit-less records survive save/stream/assign but were DROPPED by the merge → any hero-side state without the own bit never reached the UI copies.
- HEAL MERGE FIX (build_heal_merge_fix.py, applied 2026-08-21): merge gate @0x5574F533 (5B) → cave_mrg @0x55812B00: source bit → normal; else for id 0x2F with a source healing rec → clone rec onto dest (Remove+Clone+Add, PIC) WITHOUT setting the dest bit, return al=0. Propagates the item-healing daily-used state to every UI copy (innate healing propagated natively via its bit — that's why it always updated immediately).
- Diag tooling: patch scripts\heal_probe.py (scan live process for THero/TLeader, dump healing bits/recs/items), ref_probe.py (who references an object, classifies holder by VMT). Delphi instance VMT = classname-ptr location + 32 (NOT +44). Inventory merged-HasAbility leg 0x557861A4 and enabled leg 0x55786154 both filter [item+0x34]==6; carried-items legs don't filter.
- ⚠ TItem CARRIER BACKREF EXISTS (found 2026-08-21, contradicts earlier "no backref" belief): [item+4] = owning container (THeroItems/THeroInventory), [container+4] = carrying THero/TLeader. Verified on live server+client copies. Use for any item→hero resolution.
- CARRIER FIX (build_item_healing_carrier.py, applied 2026-08-21, FINAL piece): overland unit window builds names via TAbstractUnit.ListAbilityInfo 0x5577FA50 → owner = [unit vmt+0x154] owner-finder best (the ITEM for item-granted) → ability.GetName(item) — bypasses THero.GetAbilityName/cave_gan. cave_ghe2 @0x55812B80 (VMT+0x74 repoint, supersedes cave_ghe 0x55812700 which is now orphaned): item owner → resolve carrier via backref chain (class-checked, delta-normalized) → carrier's rec gates. Item-healing "(used)" display verified working in-game.
- ⚠ LIVE-INJECTION LESSONS (2 crashes caused, both repaired): (1) logger/scratch caves in the mapped image must NOT overlap file caves (clobbered cave_mrg tail once); (2) the game's OWN threads cannot write image CODE-section pages (EXECUTE_READ) — any injected code that stores to in-image buffers needs VirtualProtectEx PAGE_EXECUTE_READWRITE first, else the first hooked call AVs (looked like "0 calls logged" + delayed crashes). WriteProcessMemory from outside succeeds via COW regardless — deceptive. Injectors in scratchpad: inject_gnamelog.py / inject_more.py (loggers @0x55812E00+, RWX'd, free-region guard), repair_live.py, hot_apply_ghe2.py, dump_owner.py, poke_used.py.

**Why:** any future ability/level/item feature builds on these exact offsets and semantics.

**How to apply:** for new leveled abilities keep the convention "no record → level 1 when bit present"; use DM's GetLevel as the reference shape. Related: [[aowx-project-overview]], [[aowx-exe-string-pipeline]].
