TLeadershipAbility VMT 0x55722008 (flyweight, id 0x2E). Per-owner TLeadershipAbilityData record: [+0xC] own level, [+0xE] id, [+0x10] borrowed (aura) level, [+0x14] source name. Methods: GetLevel +0x70 0x557661C4 (→ our cave_findrec 0x55812440: max(own, borrowed), item-aware), attack-bonus +0x5C 0x557661FC and defence-bonus +0x60 0x55766210 (level → byte tables 0x5580E0C0 / 0x5580E0C8, 5 entries, the project's 4-level port), GetSourceName +0x8C 0x55766348, GetInherent +0x90 0x55766384, CanExpand +0xC4 0x557663A8 (own < cap [abil+0x28]), GetLevelName +0x10C → cave 0x5580E020. SetExternalSource 0x55766224 (eax=abil, edx=unit, cl=level, stack=name; creates record own=0 + sets bit; writes name/borrowed only if own<level; ret 4). ResetExternalSource 0x557662E4 (own==0 → SetAb 0 + RemoveAbilityData; else clear name, borrowed=0).

Bonus consumers: TAbilityOwner.GetAttackBonus 0x5574F624 / GetDefenceBonus 0x5574F674 sum [abil+0x5C]/[+0x60](abil, owner) over abilities with the OWN bit ([vmt+0x88]). Unit stats (TUnit.GetAttack 0x557829EC etc.) do NOT include Leadership; the aura only enters through these sums.

Aura recompute: TArmy.UpdateFormation 0x5578D034 (from TArmy.Update 0x5578D1B0 and TCombatUnit.SetParty): pass 1 per unit ResetExternalSource + max1 of [vmt+0x144] GetAbilityLevel(0x2E) (+ name via [vmt+0x60]); vanilla pass 2 0x5578D128..0x5578D186 gave max1 to every unit below it (⚠ 0x5578D162 carries a .reloc entry — hook only the first 6 bytes).

**REWORK APPLIED 2026-09-13** (`patch scripts\patch_leadership_others_v1.py`, backup `.bak_leadership_others`, caves 0x55815D00–0x55815DF3): (A) both bonus getters `call cave_blevel` = owner record's BORROWED field only → self never benefits; (B) pass 2 replaced by cave_pass2 (hook 0x5578D128 → exit 0x5578D186): count of max1 holders + max2; target = (own==max1 && count==1) ? max2 : max1; SetExternalSource(target) then force [rec+0x10]=target (SetExternalSource skips when own ≥ target). Rule: bonus = highest own level among OTHER party members; co-leaders buff each other; lone leader gets 0. (C, added same day after the user's editor test) GetLevel's record tail at 0x55812464 (inside the item-ability-levels cave) now returns OWN only, never borrowed: with max(own,borrowed) the map editor showed a Leadership-I leader as IV beside a Frost Queen, offered V, and deleting "IV" left a bare bit (no record) → "Leadership, cost -5" in pre-game customise (Clear fixes it). ⚠ Any unit whose ability list shows a bare "Leadership" with no level record is that corruption — vanilla editor behaviour on delete. Followers under an aura now list plain "Leadership" (level 0) + the received bonus. Script applies/reverts per site (upgrade in place).

Second rebuild same day (caves now 0x55815D00–0x55815EEB): (1) ⚠ TUnit CACHES its ability bonuses in [unit+0x44..0x47] via VMT+0x90 "AbilitiesChanged" (0x55782B34 → TAbilityOwner.GetAttackBonus 0x5574F624 / Def 0x5574F674 / +0x46 / +0x47); THero computes live (THero.GetAttack 0x55788360 → cave 0x5580F100). SetExternalSource fires +0x90 BEFORE cave_pass2's direct borrowed write, so a non-hero top leader (Frost Queen IV beside a Leadership-III leader) showed no bonus until cave_pass2 re-fired [vmt+0x90] after the write. General rule: after touching any unit ability record/bit, call [unit vmt+0x90]. (2) Display: TLeadershipAbility VMT+0x58 (slot 0x55722060, reloc'd) → cave_lname: ML.GetName (own-level name via 0x55765298 → GetLevelName cave 0x5580E020) + " (+<roman> received)" when the record's borrowed field is set, e.g. "Leadership III (+IV received)", follower "Leadership (+IV received)". Literals embedded as Delphi AnsiStrings (refcount -1) with a PIC pointer table; _LStrCat3 0x55701190 (eax=@dest, edx=s1, ecx=s2), _LStrAsg 0x55701150, _LStrClr 0x55701140. In-game retest pending.

**2026-09-17 in-game test: followers (swordsmen) got NO bonus while units with an own level did.** Proven with `patch scripts\leadership_probe.py` (scans live TUnit/THero/TLeader, groups by party, prints bit/record/cache) + `diag_hwbp.py` (debugger-attach hardware write-watchpoint; 0 writes to the follower's bit dword during a formation change): followers held a record (own 0, borrowed N, source name) but the ability BIT was clear and the cached bonus 0. Cause = change C: pass 1 only resets/removes a unit when it has the bit OR GetAbilityLevel>0; with own-only GetLevel a bit-less record (records stream/copy bit-independently, e.g. save/load) is never removed, so pass 2 finds it, skips SetExternalSource's create+SETBIT path and only rewrites borrowed; the bonus sum is bit-gated → 0. Fix in the same script (v1 upgraded in place, "stale" detection for older cave bytes, zone 2 0x558162E0–0x55816400 for cave_lname + cave_p1gate): E pass-1 gate call @0x5578D096 → cave_p1gate = max(own,borrowed) from the own record else original GetAbilityLevel; F cave_pass2 forces the bit via [unit vmt+0x50](0x2E,1) after SetExternalSource. Asm helper gained `jmp32` (loop 2 body > 127 B). TUnit ability bitset: [unit+8] → dwords, [unit+0xC] count (146); id 0x2E = dword1 bit 14. VMT layout: classname −0x20, instance size −0x1C, parent −0x18; TUnit size 0x48, THero 0x9C, TLeader 0xA4.
