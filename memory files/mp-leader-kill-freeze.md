## ROOT CAUSE FOUND LIVE 9/3 (hangprof.py EIP sampler on the frozen process, PID attach, NO elevation needed this time)
Main thread spinning: `TCombat.Finalize -> TAoWHSMap.GameOver -> TPlayerControl.GameOver -> TSimultaniousPlayerControl.SetPlayerGameOverStatus -> TPlayer.SetGameOverStatus -> TPlayerMagicControl.RemoveEnchantments @0x5577CB9C (while Count>0: ExecuteDispelEnchantment(Count-1)) -> TUnitEnchantment.Dispel @0x55765E14 -> TUnitControl.FindUnit @0x5577E948 -> nil -> Dispel EXITS WITHOUT REMOVING -> Count never drops`. **VANILLA bytes at every site** (== AoWEPACK.dpl). Not our patch; not combat-mode specific; a fresh game can't repro because it needs an orphan.
- The orphan (read live): TUnitEnchantment, **caster [+0xC]=3, unit id [+0x18]=0, ability [+0x1C]=0x9B**, upkeep [+0x10]=2, [+0x14]=10, ench id [+8]=0x03000003, in player 3's list ([player+0x54] TPlayerMagicControl -> [+0x3C] TEnchantmentList (TENode) -> children TEObjectList at [list+8] (TList-derived: +4 items, +8 count)). Other players' TUnitEnchantments (0x9A/0x9B/0x9E/0xA9) all had valid unit ids. HOW the id became 0 is still unknown (TUnitEnchantmentAbility.Expand copies [unit+0x18] into [ench+0x18] and asserts >0; only writer found). Candidates: unit copies / resurrect-animate paths / older save format. Save with the orphan: `X\Save\AoWx - After the Fall.asg` + autosave.asg (9/3 02:28) - parse for class 0x2130F tag 0x15 if the origin matters later.
- **Live unfreeze that WORKED**: WriteProcessMemory count 1->0 on that TList ([children+8]) -> game resumed instantly. Generic reader `patch scripts/enchprobe_players.py` dumps every player's enchantment list from the AoWHSMap global (RVA 0x1FA040 + live base; hardcoded PID/base - edit before use).
- **Enchantment registry RE**: TAbstractUnit.Activate -> RegisterEnchantments @0x5577F2A4 (each enabled TUnitEnchantmentAbility with caster>=0 -> RegisterEnchantment(caster.mc, [data+0x10])); Deactivate/Killed -> UnregisterEnchantments; TUnitEnchantmentAbility.Remove -> Unregister + RemoveAbilityData (TUnitEnchantmentAbilityData.Destroy FREES [data+0x10]); TEnchantment.SetSource re-registers on caster change; ValidateEnchantmentID assigns (player<<24)|seq. Register/Unregister = raw TList IndexOf / Add(list vmt+0x70) / Remove on the children list + Update. TEnchantment.Dispel base = `xor eax,eax; ret`; TUnitEnchantment.Dispel = FindUnit -> unit.RemoveAbility vmt+0x98 (TAbstractUnit.RemoveAbility -> TAbilityOwner.RemoveAbility -> ability vmt+0xD4 Remove).

## ROOT CAUSE = OURS (user tip 9/3: Nate had a Spirit Puppet that PERSISTED after a Recall Spirits combat; "this bug didn't exist before")
`patch_summoned_ability_v5.py` (TRecallSpiritCA/TAnimateDeadCA caves, file 0x10BAD2/0x10BB08) grants the combat-spawned unit the **Summoned ability 0x9B** via: `mov [unit+0x18],1` (fake id to pass Expand's assert) -> ExpandAbility(0x9B) -> `mov [ench+0x18],0` ("clear source unit ID" - THE BUG) -> SetSource(player) -> RegisterEnchantment. When the spawn persists after combat (recall-spirit/animate-dead persist patches), Activate -> RegisterUnit gives the unit a real id (id 1 collides -> internal "UnitID Failure" exception, caught -> GetFreeID) but the enchantment keeps 0 -> Dispel/FindUnit can never find it -> undispellable Summoned effect + the defeat livelock. Applies to EVERY unit type both spells spawn.
**Fix `patch scripts/build_summoned_unitid_fix.py` (.bak_summonuid) APPLIED 9/3 to dev + 408 install:** hook the `call RegisterEnchantment` @0x5577F318 inside TAbstractUnit.RegisterEnchantments (runs in Activate right after RegisterUnit, edi=unit, edx=ench) -> cave3 @0x558155E0 (14B): `[ench+0x18] := [unit+0x18]` then the call. Heals every path incl. old saves on load (if load activates units - verify). Awaiting user test: spawn via Recall Spirits/Animate Dead, keep alive past combat, Dispel Magic it, defeat/surrender owner.
